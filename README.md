# pyproxy

纯 Python 标准库实现的 **HTTP 反向代理与负载均衡器**。零第三方依赖。

![License](https://img.shields.io/badge/license-MIT-blue)
![Dependencies](https://img.shields.io/badge/dependencies-0-brightgreen)
![Tests](https://img.shields.io/badge/tests-272-blue)

多后端转发、四种负载均衡策略、主动健康检查、带幂等性约束的失败重试、按 IP 的令牌桶限流、
Web 管理界面与结构化访问日志——全部只用标准库。**不需要 `pip install`，克隆下来就能跑。**

项目状态：个人项目，功能完整、测试齐全，但**不追求生产级**——边界写得很清楚，
见文末「已知限制」。这个 README 的原则是**只写做到的事**。

---

## 特性

**负载均衡**

- 四种策略：`round_robin` / `random` / `weighted_round_robin`（nginx 同款平滑算法）/ `weighted_random`
- 只从**健康**的后端中挑选；一个可用的都没有时返回 `None`，由调用方转成 `503`——**不抛异常**

**故障处理**

- **主动健康检查**：后台守护线程周期探测，**连续失败 N 次**才剔除、**连续成功 M 次**才恢复，防状态抖动
- **带约束的失败重试**：只重试幂等方法、必须换一台后端、响应已开始回写就不再重试
- **`POST` / `PATCH` 绝不重试**——重试一个下单请求就是重复扣款

**协议正确性**

- 完整的逐跳首部剥离（RFC 7230 §6.1 的 8 个字段，**外加 `Connection` 里点名的任何字段**）
- 请求与响应**两个方向**都解开分块编码并重新计算 `Content-Length`
- 重复首部（如多个 `Set-Cookie`）**逐个转发**，不合并成字典
- 接受 absolute-form 请求行；保留客户端原始 `Host`；补 `X-Forwarded-*`

**运行时**

- 按客户端 IP 的**令牌桶限流**，超限回 `429` 并带 `Retry-After`
- **Web 管理界面**（后端状态、转发计数、成功率、重试次数、限流命中），**只对回环地址开放**
- **结构化访问日志**，与诊断日志分离（同 nginx 的 `access_log` / `error_log`）
- **优雅退出**：`Ctrl+C` 停线程、关日志、关套接字；连按两次强制退出

## 快速开始

**零第三方依赖，只要一个 Python 解释器。** 本项目在 Python 3.14 上开发与完整验证，
`Dockerfile` 基于 3.12（未在更低版本上实跑过）。

```bash
git clone <仓库地址>
cd pyproxy

# 一条命令跑起来：起 3 个模拟后端 + 代理
python demo.py

# 想看重试与故障转移，加一个故意不监听的坏后端
python demo.py --dead

# 想看限流，每个 IP 每秒 10 个令牌
python demo.py --rate-limit 10

# 也可以分开起（后端各占一个终端）
python mock_backend.py -p 8001 -n A
python mock_backend.py -p 8002 -n B
python run.py -b 127.0.0.1:8001,127.0.0.1:8002:2 -s weighted_round_robin

# 跑测试（272 项，约 2 分钟）
python -m unittest discover -s tests -t .
```

## 命令行参数

```
基本      -c/--config  --listen-host  -p/--listen-port  -b/--backends  -s/--strategy
转发      -t/--timeout  -r/--max-retries
健康检查  --health-interval  --health-timeout  --health-path  --no-health-check
限流      --rate-limit RPS  --rate-burst N
日志      --log-file  --quiet  -v/--verbose
其他      --print-config
```

`-b` 的写法与配置文件里的字符串形式一致。`--rate-limit 20` 会**顺带把限流打开**
（不写 `--rate-limit` 就是关闭）。`--print-config` 打印最终生效的配置后退出、不启动服务——
排查「我到底跑的是哪份配置」时最省事。

所有参与覆盖的参数默认值都是 `None`，用来区分「用户显式传了值」和「用户没传」；
后者不能覆盖配置文件。空格串等同于没传。

`demo.py` 的参数更少，是为演示准备的：`-n`（后端数量）、`-p`、`-s`、`--dead`（加一个故意连不上的
后端）、`--rate-limit`、`--rate-burst`、`--no-health-check`、`--log-file`。

## 配置文件

优先级：**命令行参数 > 配置文件 > 内置默认值**。

### 配置文件

`python run.py -c config.json`。JSON 对象，**只覆盖出现过的键**，没写的保持默认：

```json
{
  "listen_host": "0.0.0.0",
  "listen_port": 8080,
  "strategy": "weighted_round_robin",
  "timeout": 5.0,
  "max_retries": 2,
  "log_file": "logs/access.log",
  "log_stdout": true,
  "backends": [
    {"host": "127.0.0.1", "port": 8001, "weight": 3},
    "127.0.0.1:8002:2",
    "127.0.0.1:8003"
  ],
  "health_check": {
    "enabled": true,
    "interval": 3.0,
    "timeout": 1.0,
    "path": "/health",
    "unhealthy_threshold": 3,
    "healthy_threshold": 2
  },
  "rate_limit": {"enabled": false, "capacity": 20, "refill_rate": 10.0}
}
```

后端三种写法等价：`"host:port"`（权重 1）、`"host:port:weight"`、`{"host": …, "port": …, "weight": …}`。
也可以整个用逗号分隔的字符串：`"127.0.0.1:8001,127.0.0.1:8002:2"`。

| 键 | 默认 | 说明 |
|---|---|---|
| `listen_host` / `listen_port` | `0.0.0.0` / `8080` | 监听地址与端口 |
| `strategy` | `round_robin` | `round_robin` / `random` / `weighted_round_robin` / `weighted_random` |
| `timeout` | `5.0` | 转发超时（秒），只保护「代理 → 后端」这一段 |
| `max_retries` | `2` | 失败后最多再试几次；总尝试次数上限是 `1 + max_retries` |
| `backends` | 无（必填） | 至少一个 |
| `health_check.*` | 见上表下方的示例 | 依次是 `enabled` / `interval` / `timeout` / `path` / `unhealthy_threshold` / `healthy_threshold`。`timeout` 不得大于 `interval` |
| `rate_limit.*` | 关闭 | `capacity` 是桶容量（突发额度），`refill_rate` 是每秒补充的令牌数 |
| `log_file` / `log_stdout` / `verbose` | 无 / 开 / 关 | 访问日志的去处与诊断日志级别。`demo.py` 默认写 `./logs/access.log`，`run.py` 默认不写文件 |

### 校验

`validate()` 在**启动前**就把不自洽的配置打回去，而不是让它变成一个运行期才发作的怪毛病。
几条值得说的：

- 未知策略名直接拒绝，并把可选值列出来。
- `health_check.timeout` 不得大于 `interval`：探测还没超时下一轮就开始了，会堆积探测线程。
- 关掉健康检查时不再挑剔 `path` 是否以 `/` 开头；关掉限流时不再校验 `capacity` / `refill_rate`。
  **关掉的功能不该还管着配置。**
- 后端地址重复直接拒绝——重复意味着实际权重会被静默算成两倍。
- `max_retries` 可以是 0（不重试是合法选择），但不能是负数。

错误一律是 `[配置错误] 具体原因` 打到 stderr、退出码 2，不带堆栈。

## 架构

### 进程与线程

单进程。四类线程：

| 线程 | 数量 | 职责 |
|---|---|---|
| 主线程 | 1 | `serve_forever()` 接受连接；收到信号后负责收尾 |
| 请求线程 | 每连接一个 | 处理该连接上的请求。HTTP/1.1 长连接下，一条连接上的多个请求由**同一个**线程顺序处理 |
| 健康检查线程 | 0 或 1 | 周期探测后端，维护健康状态机 |
| 信号线程 | 0 或 1，瞬时 | 信号处理函数里另起一个线程去调 `shutdown()` |

必须是 `ThreadingHTTPServer` 而不是 `HTTPServer`：后者单线程串行，一个慢请求就能把整个代理
堵死——代理本身就是靠并发转发吃饭的。工作线程都是 daemon（`daemon_threads = True`），
主线程退出时不被它们拖住。

`shutdown()` 为什么必须在**另一个**线程里调：它会一直等 `serve_forever()` 退出，而后者占着
当前线程，直接在信号处理函数里调就是死锁。所以处理器里
`threading.Thread(target=server.shutdown).start()`。

### 模块依赖

单向，`config` 谁都不依赖；`server.py` 是唯一知道「一次转发长什么样」的地方；`run.py` 只做
装配与生命周期，不含业务逻辑。

```
config  <-  balancer / health / ratelimit / admin / access_log
        <-  server.py  <-  run.py
```

### 并发模型

共享状态有三处，保护方式各不相同：

1. **后端的运行时字段**（`healthy` / `current_weight` / `effective_weight` / `total_requests` /
   `consecutive_*`）。健康检查线程只写 `healthy` 与两个 `consecutive_*`；请求线程读写
   `current_weight` 与 `total_requests`。后者由负载均衡器在自己那把锁下访问。而 `healthy` 是
   **单次属性读取**，在 CPython 下是原子操作，所以请求线程读它时不需要和健康检查线程共用一把锁
   ——为一次布尔读取去抢锁，代价比它保护的东西还大。
2. **统计计数器**（总请求数、字节数、状态码分类、重试次数）：`ProxyContext` 自带 `_stats_lock`。
   这些是跨请求线程累加的，少一个锁就会丢数——有并发用例钉住：5 个线程各发 20 个请求，
   必须恰好计到 100。
3. **令牌桶表**：`RateLimiter` 内部锁；惰性补充，没有定时器线程。

请求级状态（`_response_started` / `_body_consumed` / `_reframed` / `_stats_skipped` 等）写成
「类属性声明、实例属性使用」，每条请求开头由 `_reset_state()` 重置。它们不跨线程共享：
一条连接只属于一个线程。

## 转发流程

### 一条请求的完整路径

```
accept → 请求线程 → 解析请求行与首部
                     │
                     ├─ 是 /__admin？ ──是→ 回环客户端？→ 渲染页面 / 404   ┐ 不读
                     │                                                        │ 请求
                     ├─ 被限流？ ──────是→ 429 + Retry-After                ┘ 正文
                     │
                     ├─ 读请求体（Content-Length 或分块解码；超 64 MiB → 400）
                     │
                     └─ 循环：选后端（排除已试过的）→ 建连 → 转发 → 收响应
                                │                                   │
                                │                              成功 → 回写响应
                                │                                   │
                                └─ 失败且允许重试 ←────────────────┘
                     │
                     finally: 写访问日志 + 累加统计
```

管理页与限流都拦在**读请求体之前**：这两条路都不需要正文，先把可能很大的一坨读进内存再拒绝
纯属白费——而「白费带宽和内存」恰恰是限流本身要防的东西。

统计在响应的 `finally` 里累加，和 nginx 的 `access_log` 同一时序：客户端**先**拿到响应，
统计**后**落地。所以「发完请求立刻读统计」本质上是个竞态，用例里的 `wait_for_stats()` 就是
为此存在的。

### 首部处理

**客户端 → 后端**

| 处理 | 为什么 |
|---|---|
| 剥掉 RFC 7230 §6.1 的 8 个逐跳首部，**外加 `Connection` 里点名的任何字段** | 逐跳首部只在**一段**连接上有意义。`Connection: X-Custom-Hop` 这类自定义逐跳字段同样得剥，只查固定名单会漏 |
| 剥掉旧的 `Content-Length`，分块解码后重算 | 用了 `http.client` 之后长度信息只有代理自己知道；透传旧值会让后端读到截断或挂死 |
| 追加而非覆盖 `X-Forwarded-For` | 链路前面可能还有别的代理，覆盖会把原始客户端丢掉 |
| 加 `X-Forwarded-Host` / `X-Forwarded-Proto` | 原值另存一份，后端做重定向时要用 |
| **保留客户端原始 `Host`** | 后端可能靠它做虚拟主机路由。`http.client` 默认会用后端的 `host:port` 覆盖掉，所以必须 `skip_host=True` |
| 加 `Connection: close` | 本代理每个请求新建一条到后端的连接，用完即关 |

最后一条要展开一句，因为这里容易误判：这是代理为**自己到后端那一段**新生成的逐跳首部。
所以后端**永远**看得到 `Connection`——那说明代理在正常工作，不是「漏了」。逐跳的语义是
「每段连接各管各的」，不是「这个字段名在任何地方都不许出现」。区分方法是看**内容**：
代理自己只会写 `close`，出现别的词才说明客户端发的东西活到了后端。

**后端 → 客户端**

同样剥掉逐跳首部（包括后端 `Connection` 里点名的字段），同样重算 `Content-Length`
（`http.client` 已经把分块解开了）。`HEAD` / `204` / `304` 不写响应体，但 `HEAD` 的
`Content-Length` 保留后端给的原值——它描述的是 GET 会返回多少，不能当成 0。

重复首部（比如多个 `Set-Cookie`）逐个转发，不合并成字典——合并会把它们吞掉只剩一个，
登录态直接坏掉。

### 重试

四条约束，任何一条不成立就不重试：

1. **只重试幂等方法**：`GET` / `HEAD` / `OPTIONS` / `PUT` / `DELETE`。`POST` / `PATCH`
   **绝不重试**——POST 通常意味着「创建」「下单」「支付」，后端可能已经处理完才断开连接，
   重试会真的产生第二笔订单。这是整个代理里最重要的一条安全约束。
2. **必须换一台后端**（`select(exclude=已试过的地址)`）。在同一台机器上重试毫无意义：
   那台真挂了的话，重试只是把超时时间叠加起来。过滤放在 `select()` 里而不是让调用方反复重选，
   是为了让 `total_requests` 只在真正选定一台时加一、不虚增计数。
3. **响应一旦开始回写就不再重试**。标记是在拿到响应时就置位的，不是等到 `end_headers()`
   ——因为中间任何一步抛异常，状态行都已经在缓冲区里了；此刻若不置位，重试逻辑会往同一个
   缓冲区再写一条状态行，客户端收到两条拼在一起的报文。
4. **后端自己回的 5xx 不重试**：那是业务响应，不是转发失败，重试只会打扰它。

重试之间**不睡退避（backoff）**：换后端重试是「另一台机器可能还活着」，等一会儿并不会让它
更可能活过来，只会白白增加客户端看到的延迟。

### 错误码

| 码 | 含义 |
|---|---|
| `502` | 连不上后端（拒绝连接、DNS 失败、连接被重置） |
| `504` | 后端在 `timeout` 内没有响应 |
| `503` | 没有可用后端（全被健康检查剔除 / 全试过了 / 没配置） |
| `429` | 客户端超速，带 `Retry-After` |
| `400` | 客户端报文有问题（正文超限、分块编码非法、长度读不出来） |
| `405` | 代理显式拒绝 `CONNECT` / `TRACE`——本代理是反向代理，不建隧道；`TRACE` 会回显请求，常被用作 XST 攻击，不转发 |
| `501` | 其它未实现的方法名（如 `PROPFIND`），由 `BaseHTTPRequestHandler` 直接返回 |

一律回 JSON，便于调用方解析。代理自己产生的 5xx 也计入统计，否则故障是隐形的。

`502` 和 `503` 的边界值得说一句：**同一个故障在不同时刻给出的码不同**。所有后端刚挂掉时是 `502`
（代理还在挨个试、挨个失败），等健康检查把它们全部剔除之后变成 `503`（代理知道没人可用，
索性不试了）。`503` 出现说明「代理已经不指望它们了」，这时候该去看管理页而不是看请求日志。

## 健康检查机制

### 状态机

```
HEALTHY   --(连续失败 unhealthy_threshold 次)-->  UNHEALTHY
UNHEALTHY --(连续成功 healthy_threshold    次)-->  HEALTHY
```

要求「连续」而不是「一次」：网络抖动、后端 GC 停顿都可能造成单次探测失败。若一次失败就剔除、
一次成功就恢复，状态会反复横跳（flapping），流量也跟着来回甩。

两个刻意的约定：

- **乐观启动**：后端初始状态是「健康」。这样代理启动后立刻可用，不必等第一轮探测跑完；
  后端若真是坏的，会在一个检查周期内被剔除。
- **恢复时把 `current_weight` 归零**。否则它会带着挂掉之前累积的加权值回来，被平滑加权轮询
  连着选中好几次——刚恢复就被打一波，很容易二次挂掉。

### 探测方式

后台**守护线程**周期跑 `check_once()`：对每个后端发一次 `GET <health_check.path>`，
`200 <= status < 400` 算健康，连接被拒 / DNS 失败 / 超时（都归在 `OSError` 下）算不健康。
响应体必须读完，否则连接无法正常关闭。

线程用 `Event.wait(interval)` 而不是 `time.sleep(interval)`——`stop()` 时能立刻醒来，
不用等满一个周期。单轮异常只记日志、不拖垮整个线程（`except Exception` 在这里是必要的：
一个后端的怪毛病不该让健康检查整体停摆）。

`check_once()` 与 `apply_result()` 都是同步的公开方法，测试直接驱动状态迁移，既不睡真实时间
也不发真请求。

### 与其他模块的边界

健康检查**只写** `healthy`，**不参与**选谁。选后端是 `balancer.select()` 的事，它只从健康的后端
里挑；一个健康的都没有时返回 `None`，由调用方转成 `503`，而不是抛异常。这样「谁病了」和
「选谁」两件事可以各自演化。

状态发生变化时通过 `on_change` 回调通知（`run.py` 用它写诊断日志），回调抛异常不会影响
状态机本身。

## 限流

按客户端 IP 的令牌桶：桶里最多攒 `capacity` 个令牌，以 `refill_rate` 个/秒补充，
每个请求拿走一个，拿不到就回 `429` + `Retry-After`。

三个实现上的选择，都是为了在真实压力下不出问题：

1. **惰性补充，不起定时器。** 每个客户端一个后台线程去补令牌，客户端一多就是几千个线程。
   改成「下次访问时按流逝时间一次算清」，代价是 O(1) 的乘法，收益是完全没有后台开销。
2. **用单调时钟（`time.monotonic`）而不是墙上时钟。** 系统对时或时区调整会让墙上时钟跳变，
   一旦往回跳，`elapsed` 变成负数，桶就会凭空多出（或少掉）令牌。
3. **桶表有硬上限（默认 10000）。** 键是客户端 IP，正常情况下会随时间无限增长——被扫段时
   几万个 IP 就能把内存吃光。回收分两步：先丢「已经补满」的桶（它和新建的桶行为完全一致，
   丢了不损失精度），不够再按最久未更新的顺序批量丢到 90%。**只做第一步是不够的**：扫段来的
   桶全是活跃桶，一个都回收不掉。回收只在桶数超上限时批量触发，不会让每个请求都背上 O(n) 的扫描。

代价是被第二步淘汰的活跃客户端会拿到一个满桶，相当于白送一次突发额度。这是内存安全与限流精度
之间的取舍，已写进「已知限制」。

## 管理界面

访问 `/<端口>/__admin` 可以看到运行状态：总请求数、成功率、4xx/5xx、重试次数、已转发字节、
每个后端的健康状态与计数、限流的放行与拦截数。纯服务端渲染 + `meta refresh` 自动刷新，
**不引任何前端资源**——一个代理的管理页不值得为它加一套构建工具链。

**这一页只对回环地址开放。** 它暴露了后端拓扑（内网地址、权重、健康状态）和限流参数，
属于典型的「给运维看、不该给公网看」的信息。远程客户端访问会拿到 **404**——不是 403，
因为 403 等于告诉对方「这里确实有东西」。探测行为本身照常记进访问日志与统计。
真要远程看，正规做法是在前面加一层鉴权或走独立端口，而不是把这一页放开。

管理页自己的访问**不计入统计**——它每 2 秒自刷新一次，计入就成了「自己看自己」导致数字暴涨。

## 更进一步：一个能跑的代理还差什么

**一个「最小可用」的反向代理很容易写**：监听端口、把请求转出去、按某个顺序挑后端——两百行
就够了。**但它在真实环境里活不过第一天。** 本项目按「这东西真的要上生产」的标准补齐了下面这些。
每一条都写了代码、都有测试，不是「设计上支持」。

**协议正确性**（不做这些，代理会静静地出错，而且很难查）

| 项 | 不做会怎样 |
|---|---|
| 完整的逐跳首部处理：RFC 7230 §6.1 的八个字段，外加 `Connection` 里点名的字段 | `Connection: X-Foo` 这类自定义逐跳字段会被原样转发给后端，语义错乱 |
| 请求与响应两个方向的分块编码都解开并**重新计算 `Content-Length`** | 用了 `http.client` 之后长度信息只有代理自己知道，直接透传旧首部会让客户端读到截断或挂死 |
| 重复首部逐个转发而不是合并成字典 | 多个 `Set-Cookie` 会被吞掉只剩一个，登录态直接坏掉 |
| absolute-form 请求行（`GET http://host/path`）剥掉 scheme 与 authority | 按 RFC 代理必须接受这种写法，不处理就把整条 URL 当路径发给后端 |
| `HEAD` / `204` / `304` 的正文语义 | `HEAD` 的 `Content-Length` 描述的是 GET 会返回多少，不能当成 0 |

**转发语义**（这些是「能跑」和「跑对了」的区别）

- **重试有幂等性约束**：只对 `GET/HEAD/OPTIONS/PUT/DELETE` 重试，`POST`/`PATCH` **绝不重试**
  ——重试一个下单请求就是重复扣款。重试还必须换一台后端（在同一台机器上重试毫无意义），
  且响应只要已经开始回写就不再重试（否则客户端会收到两条拼在一起的报文）。
- **后端自己回的 5xx 不重试**：那是业务响应，不是转发失败，重试只会打扰它。
- **错误码分语义**：`502` 连不上后端、`504` 后端超时、`503` 没有可用后端、
  `429` 客户端超速（带 `Retry-After`）、`400` 客户端报文有问题、
  `405` 不支持 `CONNECT`/`TRACE`。一律回 JSON 便于调用方解析。

**运行时健壮性**

- **健康检查防抖动**：连续失败 N 次才剔除、连续成功 M 次才恢复。一次失败就剔除的话，
  后端一次 GC 停顿就会让流量来回甩。
- **后端恢复时把 `current_weight` 归零**：否则它会带着挂掉前累积的加权值回来，
  被平滑加权轮询连着选中好几次。
- **平滑加权轮询**（nginx 同款算法）而不是「按权重切片依次发」：权重 5:1:1 时
  后者会连续发 5 次给 A，前者得到 A B A C A A A，瞬时压力更平均。
- **轮询在有后端被剔除/重试跳过后不乱序**：这里踩过真坑，两种错法分别导致
  「某台后端永远收不到请求」和「分布严重倾斜（12 次里 A 拿 5 次、B 只拿 1 次）」，
  细节和实测数据记在 `proxy/balancer.py` 的类注释里。
- **按客户端 IP 限流（令牌桶）**：容量 + 补充速率两个参数，超限回 `429` 并带
  `Retry-After`。三个实现选择都是冲着真实压力去的：**惰性补充**（不起定时器，
  否则几千个客户端就是几千个线程）、**单调时钟**（墙上时钟被对时调整会让桶凭空
  多出或少掉令牌）、**桶表设硬上限**（只回收空闲桶是不够的，扫段来的全是活跃桶，
  一个都回收不掉）。被淘汰的活跃客户端会拿到一个满桶——这是内存安全换来的代价，
  已写进「已知限制」。
- **管理页 `/__admin`**：后端健康状态、各后端转发计数、成功率、4xx/5xx、重试次数、
  限流命中与放行数。**只对回环地址开放**，远程客户端拿到 404——不是 403，因为 403
  等于告诉对方「这里确实有东西」。探测行为本身照常记进访问日志与统计。
- **优雅退出**：`Ctrl+C` 停健康检查线程、关访问日志、关监听套接字；连按两次强制退出，
  防止卡住的请求线程拖住收尾。Windows 下 `Ctrl+Break` 走同一条路径。
- **访问日志与诊断日志分离**（同 nginx 的 `access_log` / `error_log`）：
  访问日志走 stdout，横幅与告警走 stderr，所以 `python run.py ... > access.log`
  拿到的是干净的结构化日志。
- **访问日志写失败不拖垮请求**，日志文件打不开时退化为只输出终端——但只报一次，
  因为磁盘写满之后每个请求报一次，本身就成了自伤。
- **`Connection: close` 一定说出来**：HTTP/1.1 默认长连接，凡是要断开这条连接的
  路径（限流拒绝、响应已开始回写、正文不完整）都必须显式声明，否则客户端会在一条
  即将被服务端关闭的套接字上发下一个请求。这是实测踩出来的，不是推理出来的。
- **关闭前先把残留正文读掉**：Windows（及多数协议栈）在接收缓冲区还有未读数据时
  `close()`，发出的是 RST 而不是 FIN，RST 会把客户端**已收到但还没读走**的响应一起
  冲掉——拒绝一个请求时，连「为什么被拒绝」也一起拒了。所以关连接前先丢弃残留正文
  （上限 64 KiB、最多等 0.5 秒：客户端可以声称 `Content-Length: 1GB` 再慢慢发，
  不设上限就是把 DoS 请进门）。补在 `finish()` 这一个收口处，而不是各个拒绝分支里。

**可验证性**

- **272 项单元测试**，全程零第三方依赖。转发层用**真实 socket** 端到端跑，不打桩网络
  ——这一层最容易错的恰恰是协议细节，把网络换掉就什么都测不出来了。
- 1 MiB 随机二进制走完整链路后逐字节校验；分块请求用手写裸报文而不是 `http.client`
  （用库的话，万一它悄悄改用 `Content-Length`，用例照样「通过」但测的已经不是分块了）。
- 限流用例**注入时间戳**而不是 `time.sleep`：验证「等一秒补一个令牌」不该真的慢一秒，
  注入之后既是瞬时的也是确定的。
- 「远程看不到管理页」用**真实的非回环地址**验证（代理绑 `0.0.0.0`，从本机局域网地址
  连过去），而不是只单测判定函数——改不了客户端地址就等于没测。

**容器化**

- `Dockerfile` + `docker-compose.yml`：代理与 3 个模拟后端各一个容器，用服务名互相
  寻址，带健康检查与依赖顺序。镜像里没有 `pip install`——这个项目零第三方依赖，
  不需要装依赖的镜像才是最不容易在别人机器上装不出来的镜像；进程跑在非 root 下。

**这个 README 里不写没做到的事。** 上面每一条都实现并跑通了，唯一例外是容器化：
**开发机上没有安装 Docker，镜像没构建过**，只验证了「YAML 可解析」和「compose 里那条

## 已知限制

前面每一节写的都是**做到**的事。这一节写**没做到**的事，以及为什么不做——把边界说清楚
比假装没有边界更有用。

1. **按 IP 的令牌桶拦不住分布式来源。** 桶按客户端 IP 分，来自 N 个 IP 的压力就是 N 份独立
   额度。这是方案的固有性质，不是参数没调好——要拦分布式得在更前面（网关、CDN）做，
   或者换成全局配额。用例 `test_a_per_ip_bucket_does_not_stop_a_distributed_source`
   刻意把这一点钉成了文档。
2. **桶表满时，被淘汰的活跃客户端会拿到一个满桶。** 桶表有硬上限（默认 10000）。只回收空闲桶
   是不够的：扫段来的全是活跃桶，一个都回收不掉，所以满了以后按最久未使用批量淘汰到 90%。
   代价是被淘汰的客户端下次来时额度过期重置。这是「内存不被打爆」换来的——宁可漏一点，
   不可 OOM。
3. **没有上游连接池。** 每个请求新建一条到后端的 TCP 连接，用完即关。好处是逻辑简单、
   没有连接复用带来的串号风险；代价是高 QPS 下端口占用与握手开销明显。
4. **请求体必须完整读进内存**，上限 64 MiB——不读全就没法重试、也没法重算 `Content-Length`。
   **响应体**则取决于后端给不给长度：给了就分片透传（按 64 KiB 一块块读、一块块写，
   不会拼成一个 `bytes`），**下载大文件不吃内存**；只有分块编码（`Transfer-Encoding: chunked`）
   的响应必须读全——因为全长要解开分块才知道。所以两件事都不适合本代理：**上传**大文件，
   以及后端用 chunked 发**大响应**。
5. **后端自己回的 5xx 不重试**，这是有意的（见「重试」第 4 条），但对某些调用方来说可能
   不是想要的行为。
6. **请求在「读完正文之前」就被拒绝、且它声明的正文超过 64 KiB 时，客户端可能收不到响应。**
   关闭连接前会丢弃残留正文以避免 RST 冲掉响应，但丢弃有 64 KiB 的上限——客户端可以声称
   `Content-Length: 1GB` 再慢慢发，无上限地读就是把 DoS 请进门。超过上限时代理放弃丢弃，
   内核缓冲区清不空，RST 躲不掉。这是「不替攻击者读完大正文」的代价，针对的是限流拒绝和
   管理页这两条不读正文的路径（需要正文的请求会把它读完，不存在残留）。
7. **容器化只在纸面上验证过。** 开发机没有安装 Docker，镜像**没有构建过**。只验证了两件事：
   `docker-compose.yml` 能被 YAML 解析，以及 compose 里那条 `--backends` 命令行能在本机
   正确解析成配置。别当它已经能跑。
8. **没有 HTTPS / TLS 终止。** 只监听明文 HTTP。`_scheme()` 目前恒返回 `"http"`——
   将来若加上 TLS 终止，改成 `isinstance(self.connection, ssl.SSLSocket)` 判断即可。

## 贡献

欢迎提 Issue 和 PR。这个项目的原则是**宁可少写功能，也不留不诚实的东西**，所以：

- **修 bug 的 PR 请带上能复现它的测试。** 判断标准很简单：**把修复代码改回去，用例应该变红**
  ——不会变红的用例不叫回归测试，只是陪跑。仓库里现有的每个 fix 都配了回归用例
  （轮询错位在 `test_balancer.py`、`CONNECT/TRACE` 的 405 在 `test_proxy.py`、
  `effective_weight` 同步在 `test_config.py`，等等）。
- **新增功能请一并补充测试**，并说明它解决了什么真实问题。
- **改动请在提交前跑一遍全量测试**：`python -m unittest discover -s tests -t .`
- 代码风格：以仓库现有风格为准。注释写**为什么**，不写**是什么**。
